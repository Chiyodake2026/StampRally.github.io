# デジタルスタンプラリー

GitHub Pages + Supabaseで公開するための最小構成です。Supabaseを正本のデータベースとし、
Googleスプレッドシートは閲覧・集計用の同期先にしています。

## 1. デモ

Supabaseを設定しなくても、`index.html?stamp=bridge` のようなURLで動作します。
この場合は端末のlocalStorageだけにスタンプを保存します。

## 2. Supabase設定

1. Supabaseで新規プロジェクトを作成
2. SQL Editorで `sql/schema.sql` を実行（何度実行しても同じ結果になります。既存のデータは消えません）
3. Project Settings > API から URL と anon/publishable key を確認
4. `js/config.js` の2項目を変更
5. GitHub Pagesへ公開

### 管理者の登録

管理画面（`admin/`）は、Supabase Authでログインし、かつ `admin_users` に登録されたユーザーだけが閲覧できます。

1. Authentication > Users > Add user で管理者のメールアドレスとパスワードを作成
2. SQL Editorで次を実行（メールアドレスを変更）

   ```sql
   insert into public.admin_users (user_id)
   select id from auth.users where email = 'admin@example.com'
   on conflict do nothing;
   ```

3. Authentication > Sign In / Providers で「Allow new users to sign up」をオフにする（第三者のアカウント作成を防ぐため）

Supabaseのダッシュボード（Table Editor・SQL Editor）からは、この設定に関係なく全データを閲覧できます。

## 3. QRコードURL

例：

- `https://あなたのサイト/index.html?stamp=river`
- `https://あなたのサイト/index.html?stamp=bridge`
- `https://あなたのサイト/index.html?stamp=fish`
- `https://あなたのサイト/index.html?stamp=island`
- `https://あなたのサイト/index.html?stamp=water`
- `https://あなたのサイト/index.html?stamp=goal`

各URLをQRコード化して、対応する場所に設置します。

## 4. 記録される内容（Supabase）

| テーブル | 内容 |
|---|---|
| `scan_events` | QRの全読み取り履歴（再スキャンも含む）。`is_first_claim` で初回取得（true）か再スキャン（false）かを区別。`user_agent` はブラウザ情報で、通信失敗後の再送は末尾に `[resend]` が付く |
| `stamp_claims` | 参加者ごとの初回スタンプ取得（取得順 `sequence` と初回取得時刻） |
| `survey_responses` | アンケート回答（満足度・印象に残った場所・自由記述・ワークショップ参加有無・景品希望）。**個人情報は含まない** |
| `prize_shipping` | 景品の発送先（氏名・郵便番号・住所・電話番号・同意した規約の版）。景品を希望した人だけ。管理者以外は読み取れない |
| `excluded_participants` | 集計・CSV・スプレッドシートから外す参加者（テストなど）。データは削除されない |
| `admin_users` | 管理画面を使えるユーザー |

6種類の `stamp_claims` が揃うとコンプリートと判定され、アンケート画面へ進めます
（判定はSupabase側の `submit_survey` 関数でも行います）。
アンケートでは、「景品を希望する」にチェックした人だけ、プライバシー規約に同意したうえで発送先を入力します。

### Supabaseのダッシュボードで読みやすく見る

Table Editor に、日本語の列名・日本時間で表示する閲覧用ビューがあります（ダッシュボード専用で、サイトからは読めません）。

| ビュー | 内容 |
|---|---|
| `ja_participants` | 参加者ごとの状況（スタンプごとの取得時刻、取得順、端末など） |
| `ja_scan_log` | 読み取り履歴（新しい順。端末の種類、初回／再スキャン） |
| `ja_surveys` | アンケート回答（個人情報なし） |
| `ja_shipping` | 景品発送先（**個人情報あり**） |

## 5. 管理画面（`admin/`）

- 概要カード：参加者数・クリア人数（クリア率）・総スキャン数（うち再スキャン）・アンケート回答（回答率）・景品希望・平均満足度・除外した参加者
- 集計：獲得数別の人数（どこで離脱しているか）、スポット別、日別、ワークショップ参加別、満足度の分布
- 参加者の一覧（取得順・取得時刻・端末）、QR読み込み履歴、アンケート。それぞれ絞り込みができます
  （履歴：参加者ID・スポット・初回／再スキャン・期間。アンケート：景品希望・ワークショップ・期間。参加者：状態・ID）
- 景品発送先（個人情報）は、「景品発送先（個人情報）」を開いたときだけ表示されます
- 30秒ごとに自動更新（チェックを外すと止まります。「さらに読み込む」で増やした履歴の件数は保たれます）
- CSV：景品発送CSV（希望者のみ）・アンケートCSV（個人情報なし）。どちらも、押した時点の最新データから作り、除外した参加者は含みません

### テストデータの除外

動作確認で読み取ったデータが集計に混ざらないよう、参加者を「除外」できます。除外してもデータは削除されず、いつでも元に戻せます。
除外した参加者は、概要・集計・CSV・スプレッドシートに含まれません（管理画面の表には「除外した参加者も表示」で表示できます）。

- 参加者ごと：参加者の表の「除外」ボタン
- まとめて：「テストデータの除外」で日時を指定すると、**その日時より前に最初の読み取りがあった参加者**がすべて除外されます。
  本番開始の直前の時刻を指定してください
- 元に戻す：参加者ごとの「除外を解除」、または「除外をすべて解除」

## 6. プライバシー規約（公開前に必ず確認）

規約の本文は `survey/privacy.html` の1か所だけにあり、アンケート画面のモーダルにも同じ内容が表示されます。
`【要確認】` の箇所（運営者名・保管期間・第三者提供・委託・問い合わせ先・開示等の手続き・データの保存場所など）は、
運営者が正式な情報を記入してください。記入後は「下書き」の注意書きを削除し、`data-version` を更新します。
アンケート画面の「個人情報の取り扱い（要点）」（`survey/index.html`）にも `【要確認】` があります。
この規約は法令への適合を保証するものではないため、千代田区・運営者側での確認を経てから公開してください。

## 7. Googleスプレッドシートへの自動同期

Supabaseを正本とし、スプレッドシートは閲覧・集計用の同期先にします（スプレッドシートからSupabaseへは書き戻しません）。
Google Apps Script（`gas/sheets-sync.gs`）が **5分ごとに「前回から変化があったか」だけを軽く確認** し、
変化がなければ何も書き換えません。変化があったときだけデータを取得して、各シートを書き直します。
GoogleのAPIキーやSupabaseのservice_role keyは使いません。必要なのは、読み取り専用の同期トークンだけです。

### 設定手順（初めて設定する場合）

1. SupabaseのSQL Editorで `select private.issue_sheets_token();` を実行し、表示された値を控える
   （再発行すると以前のトークンは無効になります。値はSupabaseにはハッシュとしてだけ保存されます）
2. 同期先のGoogleスプレッドシートを新規作成し、拡張機能 > Apps Script を開く
3. `gas/sheets-sync.gs` の内容をすべて貼り付けて保存
4. プロジェクトの設定 > スクリプト プロパティ に次を追加
   - `SUPABASE_URL`：`js/config.js` と同じURL
   - `SUPABASE_PUBLISHABLE_KEY`：`js/config.js` と同じ公開キー
   - `SHEETS_SYNC_TOKEN`：手順1の値
5. エディタで `setup` を選んで実行し、権限を許可する（タイムゾーンを日本時間に設定し、5分ごとの自動同期を設定し、最初の同期を行います）

### 作られるシート

| シート | 内容 |
|---|---|
| 概要 | 最終確認・最終更新の時刻、全体の数字、獲得数別の人数、ワークショップ参加別、満足度の分布、日別 |
| 参加者 | 1人1行（新しく動いた人が上）。状態、獲得数、**スタンプごとの取得時刻（空欄＝未取得）**、コンプリート日時、取得順、読み取り回数、端末、アンケート回答、ワークショップ参加 |
| スポット別 | 総読み取り回数、ユニーク参加者数、再スキャン回数、取得者数、取得率 |
| アンケート | 回答日時、満足度、印象に残った場所、コメント、ワークショップ参加、景品希望（新しい順） |
| スキャン履歴 | 読み取り日時（新しい順）、参加者ID、スポット、初回／再スキャン、端末の種類、再送 |
| 景品発送（個人情報） | 氏名・住所など。同期する設定にしたときだけ作られます（後述） |
| メモ・分析用 | 同期の対象外。自由にメモ・集計・グラフを作れます |

### 見方と注意

- **「概要」の「最終確認」** は、5分ごとにSupabaseを確認した時刻です。「変更なし」「更新しました」のどちらかも表示されます。
  「最終更新」は、データが変わってシートを書き換えた時刻です。止まっていないかは、この「最終確認」で分かります。
  「状態」が「正常」でなければ、原因がそこに表示されます（Googleからも失敗の通知メールが届きます）
- 同期されるシートは、**データが変わるたびに中身が書き直されます**。列の追加・並べ替え・色付けは消えます。
  自分用の集計やメモは「メモ・分析用」シートに作り、同期されるシートを参照してください
  （例：`=COUNTIF('参加者'!B:B,"コンプリート")`）
- 絞り込み・並べ替えをしたいときは、メニューの「データ → フィルタビュー」を使うと、書き直されても残ります
- 除外した参加者（テストなど）は、どのシートにも含まれません
- メニュー「スタンプラリー同期」から、「今すぐ同期」「全体を強制的に書き直す」「自動同期の開始・停止」ができます

### 「拡張機能 > Apps Script」で「ファイルを開くことができません」と出る場合

Googleの既知の不具合で、ブラウザで複数のGoogleアカウントに同時にログインしていると起こります（このプロジェクトとは無関係です）。次の順に試してください。

1. スプレッドシートを開いているアカウント以外からログアウトする、またはシークレットウィンドウで、そのアカウントだけにログインして開き直す
2. ブラウザのプロファイルを分ける（Chromeの場合は右上のアイコン > 追加）
3. 組織のGoogleアカウントの場合は、管理者がApps Scriptを無効にしていないか確認する
4. それでも開けない場合は、スプレッドシートに紐づけずに作る：
   1. <https://script.google.com> を、スプレッドシートと同じアカウントで開き、「新しいプロジェクト」を作成
   2. `gas/sheets-sync.gs` の内容を貼り付けて保存
   3. スクリプト プロパティに、上記に加えて `SPREADSHEET_ID`（スプレッドシートのURLの `/d/` と `/edit` の間の文字列）を追加
   4. `setup` を実行して権限を許可（メニュー「スタンプラリー同期」は表示されませんが、同期は動きます）

### 景品発送情報（個人情報）を同期する場合

初期設定では同期しません。同期する場合は、スクリプト プロパティに `SYNC_SHIPPING` = `true` を追加します。
個人情報を含むため、閲覧できる人を限定した**別のスプレッドシート**を用意し、
そのIDを `SHIPPING_SPREADSHEET_ID` に設定することをおすすめします（未設定ならこのスプレッドシートの「景品発送（個人情報）」シート）。
スプレッドシートの共有は「リンクを知っている全員」にしないでください。
同期をやめても、作成済みのシートは自動では削除されません（「概要」に残っていることが表示されます）。不要になったら手動で削除してください。

## 8. 更新手順（すでに運用している場合）

この版は、データベースの構造を変更します（景品発送先を `survey_responses` から `prize_shipping` に分離）。
次の順に行ってください。**SQLを先に実行し、その直後にサイトを公開（プッシュ）します。**

1. （推奨）念のためのバックアップ：Supabaseの Table Editor で `survey_responses` を開き、CSVでダウンロードして保管する
2. SupabaseのSQL Editorで、新しい `sql/schema.sql` の全体を貼り付けて実行する
   - 旧い発送先データは、自動で `prize_shipping` に移されます。移したデータを確認できない場合は、何も変更せずに中止します（エラーが出ます）
   - 何度実行しても問題ありません
3. すぐに、変更したファイルをコミットしてGitHubにプッシュする（GitHub Pagesに反映されるまで1〜2分）
   - SQLの実行からプッシュまでの間は、**古い管理画面で景品発送先が表示されません**（スタンプ取得・アンケート送信は止まりません）
4. 管理画面を開いてログインし、概要・参加者・アンケートが表示されることを確認する（画面を再読み込みして最新版にする）
5. 本番開始前に、動作確認のデータを除外する（「テストデータの除外」）
6. Googleスプレッドシート連携を使っている場合は、Apps Scriptを入れ替える：
   1. スプレッドシートの 拡張機能 > Apps Script を開く
   2. 既存のコードをすべて消して、新しい `gas/sheets-sync.gs` の内容を貼り付けて保存
   3. スクリプト プロパティは、そのまま使えます（変更不要）
   4. エディタで `setup` を選んで実行する（古い15分ごとの設定が、5分ごとの設定に置き換わります。全シートが新しい形式で作り直されます）
   5. 「概要」シートで、「最終確認」が更新され、「状態」が「正常」になっていることを確認する

## 9. デザイン（色・フォント）の設定

すきまキッズラボのブランドに合わせた色・フォント・角丸は、**[brand.css](brand.css) の1か所**で管理しています（各ページのCSSは、その変数を使います）。

| 色 | コード | 使い方 |
|---|---|---|
| メインカラー | `#30557e` | 見出し・主要ボタン・重要な文字（白の上で 7.7:1） |
| サブカラー | `#4d89b7` | 進捗・補助ボタンの枠・線・アイコン・スタンプの状態 |
| アクセントカラー | `#62adca` | アクセント・アニメーション・進捗の強調 |
| 白 | `#ffffff` | 背景・カード・暗い面の上の文字 |

- サブカラー（白の上で 3.8:1）とアクセント（同 2.5:1）は、文字の読みやすさの基準に届かないため、**小さな文字には使わず**、線・アイコン・図形・大きな文字にだけ使っています。
- 背景や罫線の淡い色は、上の色を白に重ねた色です（`brand.css` の `--tint-…`）。
- 管理画面のエラー表示だけは、見落とさないよう赤を使っています（管理画面のみ）。

### フォント

- **欧文・数字・英語ラベル：Josefin Sans Bold**（Google Fontsから読み込み。SIL Open Font License で、無料で商用利用できます）。
  フォントファイルはリポジトリに含めていません。表示のたびに、Google（fonts.googleapis.com）へ通信が発生します（規約の下書きにも記載済み）。
- **日本語：筑紫A丸ゴシック**。有料のフォントなので、**フォントファイルはリポジトリに含めていません**。
  - **Mac：** macOSに標準で入っているため、そのまま筑紫A丸ゴシックで表示されます（端末にあるフォントを使うだけで、配布はしていません）。
  - **iPhone・Android：** 標準では入っていないため、`brand.css` の代替フォントで表示されます（iPhoneはヒラギノ丸ゴ、Androidは端末の標準の日本語フォント）。**筑紫A丸ゴシックではありません。**
  - **すべての端末で筑紫A丸ゴシックにする場合：** Webフォントの契約が必要です。提供元は、Adobe Fonts（Creative Cloudの契約。「Web Project」で利用）、FONTPLUS、Fontworks LETS です。
    契約後、発行された読み込みタグ（例：`<link rel="stylesheet" href="https://use.typekit.net/（キットID）.css">`）を、
    `index.html`・`survey/index.html`・`survey/privacy.html`・`admin/index.html` の `<head>` に追加します
    （`brand.css` のフォント指定には、Adobe Fontsの名前 `fot-tsukuardgothic-std` を先頭に入れてあります）。
    Adobe Fontsでドメインを登録する設定がある場合は、公開URL（URLを変更したときは新しいURLも）を登録してください。
  - 実際にどのフォントで表示されているかは、ブラウザの開発者ツール（要素 > フォント）で確認できます。

## 10. 進捗バナーと景品の表示

スタンプラリー画面の上部のバナーに、取得数と、景品を希望できるまでの残り個数を表示します。

- 残り個数 ＝ 必要なスタンプ数（**6**＝全スタンプ。`js/app.js` の `PRIZE_REQUIRED`）− 取得済みのスタンプ数
- 文言は、取得状況で切り替わります：0個「スタンプを集めて、景品の希望に進もう！」／途中「あと◯個で、景品を希望できるよ！」／残り1個「あと1個！景品の希望まで、あと少し！」／6個「コンプリート！景品を希望できる条件を達成したよ！」
- このリポジトリで定義されている条件は、「6個すべて取得するとアンケート（景品の希望）に進める」ことだけです。**景品の在庫や受け取り条件は定義されていない**ため、「景品がもらえる」とは書かず、「景品を希望できる」と表示しています。
  在庫・条件を運営側で確認したうえで、`js/rally-data.js` の `RALLY_PRIZE.notice` に補足（例：「景品がなくなり次第、終了します」）を入力すると、バナーに表示されます。
- 必要なスタンプ数を変える場合は、`PRIZE_REQUIRED` のほか、`sql/schema.sql` の `is_completed`（6個）なども合わせて変更してください。
- 「視差効果を減らす」を選んでいる端末では、アニメーションは止まり、最終の状態だけが表示されます。

## 11. スタンプポイントの場所（Googleマップ）

「スタンプポイント」の欄に、ポイントごとの名前・場所の説明・取得状態と、Googleマップへのリンクを表示します。
**住所・座標は、リポジトリには登録されていません。推測でピンは打たず、運営側が [js/rally-data.js](js/rally-data.js) に入力した内容だけを表示します。**

- 入力する項目（ポイントごと）：`description`（場所の説明）／`address`（住所）／`lat`・`lng`（緯度・経度。入力すると住所より優先）／`mapQuery`（施設名など、Googleマップで探す言葉）
- 住所・座標・`mapQuery` のどれもないポイントには、リンクを出さず「場所は準備中です。」と表示します。入力した座標が範囲外（緯度±90・経度±180を超える）の場合も、リンクを出しません。
- リンクは、Googleマップの公式の共有URL（APIキー不要・無料）です。住所や座標は、URLに入る前にエンコードされます。
  - 「Googleマップで場所を見る」：`https://www.google.com/maps/search/?api=1&query=…`
  - 「ここへの行き方」：`https://www.google.com/maps/dir/?api=1&destination=…&travelmode=walking`
  - スマートフォンでは、Googleマップのアプリが入っていればアプリで、なければブラウザで開きます。
- **地図のプレビュー**：「地図を表示」を押したときだけ、ピンを打った地図（Googleマップの埋め込み）を読み込みます（ページの表示速度のため、最初は読み込みません）。APIキーは使わないため、課金は発生しません。
  この埋め込みの形式は、Googleの公式のAPI（Maps Embed API、キーが必要）ではないため、将来Googleが変更すると表示されなくなる可能性があります（その場合も、上のリンクは使えます）。使わない場合は、`RALLY_SPOTS_PREVIEW` を `false` にします。
- **全ポイントをまとめた地図**：Googleマイマップなどの共有URLを `RALLY_SPOTS_OVERVIEW_URL` に入力すると、「全ポイントの地図を開く」を表示します。**6か所すべての場所が入力されているとき**だけ表示されます（Googleマップ以外のURLは無視します）。
- 場所を公開してよいか（会場・設置場所の都合）は、運営側で確認してから入力してください。

## 12. 公開URLを変更する場合（調査結果）

現在の公開URLは `https://koeisuzuki.github.io/Chiyodake/` です。GitHub PagesのURLは「アカウント名＋リポジトリ名」で決まるため、HTMLやJavaScriptの変更だけでは、URLからアカウント名を消せません。

### 調べたこと
- リポジトリ `KoeiSuzuki/Chiyodake` は公開（public）で、GitHub Pagesが有効です。所有者は個人アカウントです。
- サイトのファイルは、すべて相対パスです（`/Chiyodake/` のような絶対パスの記述はありません）。**URLを変えても、コードの修正は不要**です。
  変更が必要なのは、`QR_URLS.txt`、READMEの例、配布済みのQRコード・リンク、SupabaseのAuth設定にサイトURLを登録している場合はその値、Adobe FontsなどでドメインやURLを登録している場合はその値です。
- 「Chiyodake2026」という名前は、調査時点で、ユーザー名としてもOrganization名としても使われていませんでした。
- GitHubの公式の説明では、リポジトリ名を変更すると、**Pagesのサイトだけは旧URLから新URLへ自動転送されません**（旧URLは404になります）。GitHubは、名前の変更に左右されないよう独自ドメインの利用を勧めています。
- ブラウザの保存データ（localStorage：参加者ID・取得済みスタンプ）は、**ドメインごと**に分かれています。ドメインが変わる方法（BとC）では、参加者の進み具合が引き継がれません。**QRコードの配布前、またはイベント開始前に切り替える**のが安全です。

### 選択肢の比較
| 方法 | 新しいURLの例 | 個人名 | 費用 | 手間 | 注意点 |
|---|---|---|---|---|---|
| A. リポジトリ名を変更 | `koeisuzuki.github.io/Chiyodake2026/` | **残る** | 無料 | 小（数分） | ドメインが変わらないため、参加者の進み具合は保たれる。旧URLは404になる |
| B. 新しいGitHubアカウントで公開 | `chiyodake2026.github.io/` | 消える | 無料 | 中 | 下記の注意。ドメインが変わる |
| C. 独自ドメイン | `（取得したドメイン）/` | 消える | ドメイン代（年額） | 中〜大（DNS設定） | URLがGitHubのアカウント名・リポジトリ名に左右されなくなり、最も安定する。ドメインが変わる |

- **Bの注意：** GitHubの利用規約では、1人が無料の個人アカウントを複数持つことは認められていません（機械用のアカウントを除く）。
  「Chiyodake2026」は、**個人アカウントではなくOrganization（組織）**として作成するのが適切です（Organizationの作成が規約上問題ないかは、念のためGitHubの規約・サポートで確認してください）。
  Organizationのサイトは `chiyodake2026.github.io` になります。リポジトリを移す場合も、コミット履歴には作成者名（SUZUKI Koei）が残ります。履歴を残したくない場合は、ファイルだけを新しいリポジトリに置く方法があります。
- **おすすめ：** URLをまだ配布していないなら **B（Organizationを作成）** が、無料で個人名をURLから消せます。予算に余裕があるなら、**将来の変更にも強いC**が最も安定します（BとCは併用できます。まずBで公開し、あとから独自ドメインを接続すれば、URLは変わらずに済みます）。
  すでにQRコードを配布済みなら、旧URLに「転送ページ」を残す必要があります（下記）。

### 旧URLから新URLへの転送
GitHub Pagesには、サーバー側の転送（301）の機能はありません。旧サイトに、JavaScriptで新URLへ移動するページを置く方法があります（`?stamp=river` などの内容も引き継げます）。

- 旧リポジトリの `index.html` に、次の内容を置きます（`新URL` を書き換えます）。旧サイトを残すことになるため、旧リポジトリは削除しないでください。

  ```html
  <!doctype html><meta charset="utf-8"><title>移転しました</title>
  <script>location.replace("https://新URL/" + location.search + location.hash);</script>
  <noscript><meta http-equiv="refresh" content="0; url=https://新URL/"></noscript>
  <p>新しいURLへ移動します：<a href="https://新URL/">https://新URL/</a></p>
  ```

- `survey/` など下の階層のURLにも対応する場合は、同じ内容の `404.html`（`location.replace("https://新URL" + location.pathname.replace(/^\/Chiyodake/, "") + location.search + location.hash)` のように、パスも引き継ぐもの）を置きます。
- 注意：転送ページは、旧ドメインから見るとlocalStorageを持っているので、必要なら参加者ID・取得済みスタンプを新URLに引き継ぐ処理を追加できます（実装には、新しいサイト側の受け取り処理も必要です）。

### GitHub側で必要な操作（いずれも、実行前に運営者の承認が必要です。このリポジトリの作業では、実行していません）
- A：リポジトリの Settings > General > Repository name で名前を変更
- B：GitHubでOrganization「Chiyodake2026」を作成 → リポジトリを作成または移転（Settings > General > Transfer）→ 公開元の設定（Settings > Pages）→ 旧リポジトリに転送ページを置く
- C：ドメインを取得 → DNSを設定（GitHub Pagesのドキュメント参照）→ Settings > Pages > Custom domain に入力し、「Enforce HTTPS」を有効にする

## 注意

同じ参加者IDで同じスタンプを再取得した場合も `scan_events` には履歴が残り、
`stamp_claims` には初回取得だけが保存されます。初回取得順はSupabase側で確定します。
